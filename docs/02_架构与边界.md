# 02 架构与边界

`OcctCSharpBridge` 的目标是提供一个**可被多个 CAD/BIM 应用复用的 OCCT Bridge**，而不是在 `main` 中实现完整 CAD 产品框架。判断一个能力是否应该进入 `main`，首先看它是否属于 OCCT 本身或 OCCT 与 .NET/UI Host 之间的稳定桥接职责。

## 1. 总体分层

```text
CAD / BIM Application
├─ Document / Feature / Entity
├─ Command / Tool / Snap / Grip
├─ Undo / Redo / Persistence
└─ Product UI / Business Rules
              │
              ▼
Reusable .NET Bridge
├─ OcctEngine
├─ OcctModelingSession
├─ Runtime / Diagnostics / Value Types
└─ WinForms / WPF / Avalonia Viewport Host
              │
              ▼
Stable C ABI
              │
              ▼
Open CASCADE Technology 7.9.0
```

## 2. `src/OcctNative`

Native 层使用 C++17 调用 OCCT，并通过 `extern "C"` 暴露稳定 C ABI，避免把 OCCT C++ 类型、模板、Handle 或异常直接暴露给 .NET。

主要职责：

- Viewer/AIS 生命周期与显示对象；
- Primitive、Curve、Surface、B-Rep 建模；
- Boolean、Feature、Healing；
- Topology、History、分析与投影；
- Mesh 与数据交换；
- 将 OCCT 结果转换成 ABI 可稳定传输的结构体、枚举、ID 和批量数组。

C ABI 保持简单：固定宽度整数、`double`、Plain Struct、UTF-8 字符串、显式 Buffer/Capacity。不要跨 ABI 暴露 STL 容器或 OCCT C++ 对象。

Native 内部头文件按职责拆分，例如 Viewer 使用 `OcctInternal.hxx`，Modeling Session 使用 `OcctModelingSessionInternal.hxx`。**已经删除的旧聚合头或兼容头不重新引入。** 调用方应包含真实依赖，而不是依赖一个重新聚合所有实现细节的 Legacy Header。

## 3. `src/OcctNet`

Managed Core 不重新实现 OCCT，而是把 Native ABI 提升成强类型 .NET API。

两个主要 Facade：

- `OcctEngine`：有 Viewer/AIS Context 的交互式场景；
- `OcctModelingSession`：无 HWND 的 Headless 建模场景。

其它核心职责：

- `OcctRuntime`：Native DLL 与 OCCT Runtime 配置、探测和诊断；
- Owner-aware Handle：阻止不同 Engine/Session 的对象被错误混用；
- `OcctGeometryExtensions`：不依赖 Native 的轻量值类型计算；
- DTO/Result 类型：把 Native 结果转换成清晰、不可误用的 Managed 语义。

## 4. Owner-aware 对象

Bridge 中的对象 ID 只在所属 Engine/Session 内有意义。

```text
OcctEngine A -> Object 12
OcctEngine B -> Object 12
```

两个 `12` 不是同一个对象。因此 Managed Handle 同时携带 Owner 身份，公开 API 在进入 Native 前验证所有权。

同样，`OcctModelShape` 不能因为 ID 相同就在另一个 `OcctModelingSession` 中复用。

## 5. Native 生命周期

`OcctEngine` 与 `OcctModelingSession` 使用 `SafeHandle` 持有 Native 根对象的释放责任，并保证 `Dispose()` 幂等。基本原则：

- 创建和销毁必须成对；
- Native 异常不能穿过 C ABI；
- 子对象使用稳定 ID/Owner 语义，不向业务层暴露任意 Native 指针；
- Dispose 后的公开 API 必须拒绝继续使用对象。

当前支持的调用模型明确为：

- 单个 `OcctEngine` / `OcctModelingSession` 实例的 Native 操作由调用方串行化，不把同一实例作为任意线程安全对象并发调用；
- `Dispose()` 不与该实例正在执行的 Native 调用并发；
- `OcctEngine` 及其 Viewer/Host 生命周期绑定创建它的 HWND/UI Thread；
- 需要后台并行几何任务时使用相互独立的 `OcctModelingSession`，不要共享同一 Session 实例。

这里**不声明 Engine/Session 的任意 Native 调用天然线程安全**。将来如果要支持同实例调用与 `Dispose()` 真正并发，需要对全部 Native 入口实施统一 SafeHandle lease/线程模型，而不是依赖一次 `IsDisposed` 检查或增加局部兼容包装。

## 6. `OcctEngine` 与 `OcctModelingSession` 不合并

### `OcctEngine`

面向交互式 Viewer：显示对象、AIS Selection、Camera/View、外观、Transform、Annotation、鼠标和视口状态。

### `OcctModelingSession`

面向几何内核和批处理：Headless 建模、拓扑查询、Boolean/Feature/Healing、Mesh、数据交换、History、Inspection、Topology Reference。

为了消除少量表面重复把两者合成巨型类，会把窗口生命周期与 Headless 建模强耦合，因此不采用。

## 7. UI Host 边界

```text
OcctNet.WinForms
OcctNet.Wpf
OcctNet.Avalonia
```

Host 只负责 UI Framework 与 `OcctEngine` 之间的适配，例如 HWND、Resize、Mouse Capture、Pan/Rotate/Zoom、Hover、Rectangle Selection、DPI 和窗口生命周期。

Host 不包含 CAD Document、Command、Feature Tree、业务 Property Panel、项目文件或专业规则。

WinForms、WPF、Avalonia 的窗口模型不同，不为了形式上的 DRY 强制建立脆弱的跨框架 UI 基类；可共享的是无 UI 依赖的交互策略，而不是具体控件生命周期。

## 8. `main` 明确不包含

- Document / DocumentManager；
- Entity / Feature Tree；
- Command / Command Registry；
- Tool / Tool Manager；
- Snap / Grip；
- Undo / Redo；
- JSON 项目持久化；
- Ribbon、PropertyGrid、Workspace 等产品 UI；
- BIM/设备专业数据和业务规则；
- OCAF/XDE。

应用如果需要自己的文档、事务和持久化模型，应在 Bridge 之上实现。

## 9. 分支职责

### `main`

可复用 Bridge、UI Host、测试、技术文档与 SDK 打包。

### `demo`

基于同一 Bridge 展示完整应用层做法和可运行示例。Demo 可以有 Document、Command、Tool 等，但这些不是 `OcctNet` API。

### `website`

项目网站，只展示公开项目能力，不参与 Bridge 运行时实现。

## 10. `main` / `demo` 手工同步规则

仓库不使用 GitHub Actions 自动同步分支。共享层变更由维护者在本地验证后**显式同步**。

必须保持一致的共享内容：

```text
.editorconfig
.gitattributes
global.json
bridge-contract.json
Directory.Build.props
src/OcctNative/**
src/OcctNet/**/*.cs
src/OcctNet.WinForms/**/*.cs
src/OcctNet.Wpf/**/*.cs
src/OcctNet.Avalonia/**/*.cs
```

不做机械同步的分支专属内容：

```text
README*
docs/**
tests/**
build.ps1
*.csproj / package policy
Demo application source
run.ps1 / publish.ps1
assets/**
```

原则是“**共享实现保持一致，分支职责保持独立**”，而不是把整个 `main` 覆盖到 `demo`。

## 11. 无旧兼容层原则

清理或重构后不保留以下形式的历史包袱：

- `Legacy*` 类型、方法或文件；
- 仅转发到新 API 的旧 Alias；
- 已删除内部头文件的同名兼容壳；
- 为旧实验目录保留的空项目或占位代码；
- 为旧 Demo API 修改核心 Bridge 设计。

如果上层 Demo 需要调整，应修改 Demo 调用方，而不是把旧接口重新塞回 `main`。

## 12. 新能力进入 `main` 的判断标准

1. 是否直接封装 OCCT 能力，或属于通用 Bridge/Runtime/Viewport Host？
2. 是否可以被多个不同上层应用复用，而不依赖具体业务 Document？
3. 是否能形成稳定、强类型、可测试的 C ABI + Managed API？

如果答案主要依赖产品数据模型、命令状态或业务流程，则留在应用层。
