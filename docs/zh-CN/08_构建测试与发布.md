# 构建、测试与发布

Bridge 3 使用同一套 ABI5-only 源码维护 Windows x64 与 Linux x64。`bridge-contract.json` 是 Bridge、ABI、OCCT、.NET 与平台要求的机器可读事实源。

## 1. 环境要求

Windows x64：

- Visual Studio 2022 / MSVC x64 C++ 工具链；
- CMake 不低于 `bridge-contract.json` 声明版本；
- OCCT **7.9.0** x64；
- 与仓库基线兼容的稳定版 **.NET 10 SDK**（`10.0.100` 或更高的 10.0.x）；
- C# 14 与 PowerShell。

Linux x64：

- C++17 编译器与 CMake；
- OCCT 7.9.0；
- 与仓库基线兼容的稳定版 .NET 10 SDK。

根目录 `global.json` 使用 `version: 10.0.100`、`rollForward: latestFeature`、`allowPrerelease: false`。因此构建允许使用后续稳定版 .NET 10 Feature Band/补丁，例如 `10.0.302`，不再要求某一个精确 SDK 补丁号。

Managed Binary SDK 以 **.NET 8**（`net8.0` / `net8.0-windows`）作为最低运行时基线，同一套 Managed SDK 面向 .NET 8、.NET 9、.NET 10 Consumer。源码仍使用 .NET 10 SDK 构建，是因为语言契约保持 C# 14。

Windows 默认 OCCT Root：

```text
D:\tools\occt-vc144-64
```

## 2. Windows build.ps1

```powershell
.\build.ps1 [Target] [Configuration] [-OcctRoot <path>]
```

Target：

| Target | 行为 |
| --- | --- |
| `validate` | 仓库静态 Contract Checks |
| `native` | 构建 `OcctNative.dll` |
| `managed` | 构建 Core、WinForms、WPF、Avalonia |
| `consumer` | 按全部受支持 .NET 8/9/10 TFM 编译 Core/Avalonia 与 WinForms/WPF Consumer |
| `test` | 构建并运行 Managed Regression Tests |
| `smoke` | Native + Managed + 真实 Core Native Smoke |
| `viewport-smoke` | 运行 WinForms、WPF、Avalonia 三套 Native Host Smoke |
| `dist` | 底层 Release Binary SDK 打包；不运行 Consumer/Regression/Smoke Gate |
| `sdk` | 经完整 Windows Gate 验证后，用已验证 Native/Managed 输出生成 `dist/win-x64` |
| `clean` | 删除生成输出 |
| `all` | 完整本地验证，包含 Consumer Matrix、Core Smoke 与三套 Viewport Host Smoke，不生成 `dist` |

推荐完整验证但不写入 Binary SDK：

```powershell
.\build.ps1 all Release -OcctRoot "D:\tools\occt-vc144-64"
```

兼容矩阵和 Viewport 可单独执行：

```powershell
.\build.ps1 consumer Release
.\build.ps1 viewport-smoke Release -OcctRoot "D:\tools\occt-vc144-64"
```

生成**经过完整验证的 Windows Binary SDK**：

```powershell
.\build.ps1 sdk Release -OcctRoot "D:\tools\occt-vc144-64"
```

`sdk` 仅支持 Release。它会在昂贵的 Native/Smoke Gate 开始前先执行源码树干净预检；若存在本地源码/配置改动，会直接打印精确的 `git status --porcelain` 条目并终止，避免完整 Smoke 全部执行后才在打包阶段失败。预检通过后，执行顺序为 Native/Managed Build → .NET 8/9/10 Consumer Matrix → ManagedTests → Core Native Smoke → 三套 Viewport Host Smoke → Binary SDK 打包。最后打包阶段直接复用已经验证过的 Native/Managed 输出，不重复构建，并再次确认源码树与 Source Commit 在整个 Gate 期间没有变化。

底层 `dist` 仍保留给只需要打包的场景，但它不代表完整 Release Gate，也不再作为 Demo 源码同步或正式 Windows SDK 验证的首选入口。

## 3. 静态 Contract Checks

除 `clean` 外的 Windows Target 都先执行仓库长期不变量检查：

| Script | 责任 |
| --- | --- |
| `tests/check-version-contract.ps1` | Bridge/ABI/OCCT/.NET/CMake/TFM/平台契约与滚动 SDK 策略 |
| `tests/check-architecture-boundaries.ps1` | Native/Managed 与 UI/Core 依赖边界 |
| `tests/check-abi5-contract.ps1` | ABI5-only，拒绝 pre-ABI5 兼容遗留 |
| `tests/check-bulk-abi.ps1` | 高基数集合保持 Snapshot/Buffer ABI |
| `tests/check-native-build-structure.ps1` | Native CMake Inventory 与平台隔离 |
| `tests/check-api-surface.ps1` | Native Declaration/Definition 与 Core `LibraryImport + Cdecl` 精确对等 |
| `tests/check-consumer-matrix.ps1` | 要求 Consumer Matrix Project 与 `bridge-contract.json` 中 `supportedConsumerFrameworks` / `supportedDesktopConsumerFrameworks` 完全一致 |

这些检查不替代编译器、Managed Regression Test 或 Native Smoke。

## 4. Consumer 兼容编译、Managed Regression 与 Native/Viewport Smoke

Consumer Matrix 是**仅编译**的真实 Consumer，不加载 OCCT，也不创建 Native Viewer：

```text
tests/OcctNet.ConsumerMatrix/OcctNet.ConsumerMatrix.csproj
  net8.0;net9.0;net10.0
  引用 OcctNet + OcctNet.Avalonia

tests/OcctNet.DesktopConsumerMatrix/OcctNet.DesktopConsumerMatrix.csproj
  net8.0-windows;net9.0-windows;net10.0-windows
  引用 OcctNet.WinForms + OcctNet.Wpf
```

执行：

```powershell
.\build.ps1 consumer Release
```

这里验证的是**同一套 .NET 8 Binary SDK 能否被 .NET 8/9/10 Consumer 编译引用**，不是为三个 TFM 生成三套 Bridge DLL。

Managed-only 回归项目：

```text
tests/OcctNet.ManagedTests/OcctNet.ManagedTests.csproj
```

执行：

```powershell
.\build.ps1 test Release
```

Core Native Smoke：

```powershell
.\build.ps1 smoke Release -OcctRoot "D:\tools\occt-vc144-64"
```

Viewport Host Smoke：

```powershell
.\build.ps1 viewport-smoke Release -OcctRoot "D:\tools\occt-vc144-64"
```

Viewport Gate 会真实创建 WinForms/WPF/Avalonia Native Host，验证 HostState、EngineGeneration、首帧 Ready、Native Handle 生命周期和基础 Viewer 操作；Avalonia Smoke 还验证 `ProjectPointToEdge` / `ProjectPointToFace` 的参数回代。

Windows 完整验证使用 `build.ps1 all Release`；完整验证后直接生产 Binary SDK 使用 `build.ps1 sdk Release`。

## 5. 滚动 .NET 10 SDK 解析

Managed 相关 Target 会从仓库根目录解析 `dotnet` Host，并按 SDK 基线与滚动策略验证：

```text
SDK contract:  10.0.100 + latestFeature
SDK resolved:  <本机稳定版 10.0.x SDK>
```

解析到的 SDK 必须是稳定版 .NET 10，且不低于 `10.0.100` 基线；不再要求 Feature Band/补丁号精确相等。例如 `10.0.302` 满足当前契约。

解析失败时应安装稳定版 .NET 10 SDK，或修复 `DOTNET_ROOT` / `PATH`。不要通过启用预览版 SDK 绕过契约。

## 6. Linux build.sh

```bash
./build.sh [target] [configuration]
```

支持：

```text
validate
native
managed
test
smoke
avalonia-smoke
dist
clean
all
```

常用命令：

```bash
./build.sh validate Release
./build.sh managed Release
./build.sh test Release
./build.sh all Release
./build.sh avalonia-smoke Release
./build.sh dist Release
```

Linux `managed` 构建 `OcctNet` 与 `OcctNet.Avalonia`；WinForms/WPF 为 Windows-only。`avalonia-smoke` 需要 X11/XWayland `DISPLAY`；普通 Native Smoke 为 Headless。新增的完整 Desktop .NET 8/9/10 Consumer Matrix 属于 Windows Gate，因为它引用 WinForms/WPF。

## 7. Binary SDK 布局

Windows `dist/win-x64` **仅包含**：

```text
OcctNative.dll
OcctNet.dll
OcctNet.WinForms.dll
OcctNet.Wpf.dll
OcctNet.Avalonia.dll
bridge-contract.json
bridge-manifest.json
```

Linux `dist/linux-x64`：

```text
libOcctNative.so
OcctNet.dll
OcctNet.Avalonia.dll
bridge-contract.json
bridge-manifest.json
```

Binary SDK 的 Managed DLL 以 .NET 8 为最低 TFM。Manifest 使用 schema 2 的嵌套 ABI5 元数据，并记录精确 `sourceCommit`、每个 Payload 文件的 SHA-256、SDK 基线，以及实际用于构建的 `resolvedSdkVersion`。旧 flat `nativeAbiVersion` 不允许重新引入。

## 8. Binary SDK 源码管理与 Consumer 同步策略

`dist/win-x64` 与 `dist/linux-x64` 是**生成构建产物，不是源码文件**。仓库只保留 `dist/README.md`；生成的 DLL/SO 包全部由 Git 忽略。

`.cache/` 在 Bridge 与 Demo 两条源码线上都必须被 Git 忽略。Demo 的 Windows 同步脚本会把可复用 Bridge Clone 保存在 `.cache/main-sdk-source/`；由于同一个本地工作区可能在 `demo-dev` 与 `main-dev` 之间切换，这个目录必须始终被视为本地构建缓存，不能让 Bridge 源码树因此变成 dirty。

这样可以避免仓库膨胀、源码/二进制不同步与跨平台 Payload 历史污染。Consumer 必须校验 Package Contract、Manifest、Source Commit 与 Hash，而不是通过 Git 历史猜测二进制是否最新。

统一 `demo` 分支遵循同一策略，将 `dist/` 视为可删除的本地缓存。Windows 从源码同步时会执行 Bridge 的 `sdk` Release Gate，并且只接受上面 7 个精确 `win-x64` SDK 文件。外部 `-SdkRoot` 中只要存在额外文件或目录就会拒绝，防止旧 DLL/未 Hash 文件混入一个表面合法的 Manifest Payload。

只有 `manifest.sourceCommit`、Contract 兼容性与全部 Hash 都匹配所选 SDK Source Revision 时，现有本地 SDK 才会复用。

## 9. 正式分发

Windows 发布验证应在干净、同步远端的正式 `main` 执行：

```powershell
.\publish.ps1 -OcctRoot "D:\tools\occt-vc144-64"
```

Linux 发布验证应在干净、同步远端的正式 `main` 执行：

```bash
./publish.sh
```

两套 publish 脚本都只负责验证和生成制品：校验正式分支/Source Revision、Release Binary SDK、schema 2 Manifest、ABI5 元数据、Source Commit 与 SHA-256。它们**不会**执行 `git add`、Commit 或 Push。Linux `publish.sh` 不允许恢复旧 flat `nativeAbiVersion` 检查或把 `dist/linux-x64` 提交进 Git 的旧流程。

验证通过后，应通过受审查的制品渠道分发，例如 GitHub Release Asset 或其它受控 Package 位置。不要把生成 Binary SDK Payload 提交到 `main`、`main-dev`、`demo`、`demo-dev`。该流程不需要 GitHub Actions。

## 10. Demo Consumer 模型

正式 `demo` / `demo-dev` 是唯一应用 Consumer 线：

- Windows x64：WinForms、WPF、Avalonia；
- Linux x64：仅 Avalonia。

Demo 当前仍以 .NET 10 为目标，用于验证最新支持的 Consumer Runtime；Bridge Binary SDK 本身以 .NET 8 为最低 TFM，因此同样可供 .NET 8/9 应用消费。Demo 会用自身 `net10.0` / `net10.0-windows` 去检查 Bridge Contract 的 supported-consumer 列表，而不是再把 Bridge 最低 TFM 当成 Demo 运行目录。Demo 不得复制 Bridge Native/Core 实现源码，也不得直接声明 `occt_*` ABI。

仅在开发验证阶段，`demo-dev` 可以显式从 `main-dev` 重建本地 Windows SDK；正式默认来源仍保持 `main`。

## 11. 文档与 API Surface 策略

`docs` 只保留手工维护的架构、使用、构建、部署与设计说明，不再生成或跟踪逐类型/逐函数 API Reference，也不再维护 API 文档生成器。

Native/Managed API 是否完整一致由 `tests/check-api-surface.ps1` 直接从当前源码验证，避免第二套生成式文档 Surface 与容易失真的硬编码接口数量。
