# 运行时部署与诊断

Bridge 3 是面向 Windows/Linux x64 的 **ABI5-only SDK**。运行时部署需要区分两个层次：

1. 第三方应用自己的 .NET 部署方式（Framework-dependent、Self-contained 或应用私有 Runtime）；
2. Bridge Native 部署（`OcctNative` + OCCT/第三方 Native Closure + OCCT Resources）。

Portable SDK 解决第二层，不替第三方应用决定 .NET Runtime 的发布方式。

## Native 文件名

```text
Windows x64: OcctNative.dll   / TKernel.dll
Linux x64:   libOcctNative.so / libTKernel.so
```

`OcctRuntime` 只解析当前平台。候选位置包括应用目录、`runtime/`、`runtimes/<rid>/native`、显式配置、`OCCT_BRIDGE_NATIVE_DIR`、受支持的 Portable 相对目录，以及启用 Repository Probing 时的仓库构建输出。

## 推荐的 Portable SDK 应用布局

```text
<app>/
  <应用 EXE 与 Managed 文件>
  OcctNet.dll
  OcctNet.WinForms.dll        # Windows，需要时
  OcctNet.Wpf.dll             # Windows，需要时
  OcctNet.Avalonia.dll        # 需要时
  bridge-contract.json
  bridge-manifest.json
  package-manifest.json       # 建议随包保留
  runtime/
    OcctNative.dll            # Windows
    libOcctNative.so          # Linux
    <OCCT 与已打包第三方 Native Closure>
  occt/
    resources/
      ...
```

在创建第一个 Native-backed 对象之前调用：

```csharp
OcctRuntime.Configure();
```

必须早于第一个 `OcctEngine` 或 `OcctModelingSession`。如果应用有明确的自定义目录，也可以使用显式 Runtime 配置。

## 不要混合最小 SDK 与 Portable Native Payload

最小 `dist/<rid>` SDK 主要用于编译引用、Source Commit/Hash 校验和受控 Consumer 构建。其根目录下的 `OcctNative` **不包含完整 OCCT Runtime Closure**。

使用 Portable SDK 发布应用时：

- 保留项目需要的 `OcctNet*.dll`；
- Native Bridge 使用 `runtime/` 内的版本，并与整个 `runtime/` 一起部署；
- 不要在应用根目录遗留另一个旧的或无依赖闭包的 `OcctNative.dll` / `libOcctNative.so`；
- `runtime/`、`occt/`、Managed DLL 和元数据必须来自同一次 SDK 构建。

`OcctNet.dll` 与 Native Bridge 必须来自同一个 Bridge Build。ABI 必须为 5；不要通过手工修改 Manifest 伪造版本或 Source Identity。

## Windows Runtime Closure

Windows Portable SDK 会收集 Bridge Native DLL、实际依赖的 OCCT DLL、必要的第三方 Runtime，以及相应 VC Runtime 依赖。目标应用应整体复制 Portable SDK Runtime，而不是依赖开发机上的 OCCT 安装路径。

## Linux Runtime Closure 与 ABI 基线

Linux Portable SDK 会收集 Bridge Native Library、打包器选中的 OCCT/TBB/FreeImage 依赖以及 OCCT Resources。包内 ELF Shared Library 使用 `$ORIGIN`，使 `runtime/` 中的同级依赖可以互相解析。

Portable SDK **不会**打包 Linux C Runtime 或完整桌面系统栈。目标系统仍需提供：

```text
glibc / libm
libstdc++ / libgcc_s
OpenGL / X11 / XWayland 相关系统库
其它平台桌面系统库
```

因此 Linux 包的兼容范围取决于 `libOcctNative.so` 和 OCCT 的 **Native ABI 构建基线**。如果在很新的 Linux 发行版上编译，生成物可能要求旧目标机不存在的 `GLIBC_*`、`GLIBCXX_*` 或 `CXXABI_*`。

若需要较广的 Linux 兼容性，应在项目计划支持的**最老 Linux/glibc 基线**上重新编译 OCCT 与 `OcctNative`，再到各目标发行版做运行验证。把一个使用新 glibc 编译的 Native 包再套进 AppImage，并不会自动降低它的 glibc/libstdc++ ABI 要求。

目标机常用诊断：

```bash
LD_LIBRARY_PATH="$PWD/runtime" ldd runtime/libOcctNative.so
readelf -d runtime/libOcctNative.so | grep -E 'RPATH|RUNPATH'
```

批量检查全部包内 `.so`：

```bash
for f in runtime/*.so*; do
  result=$(LD_LIBRARY_PATH="$PWD/runtime" ldd "$f" 2>&1)
  if echo "$result" | grep -Eq 'not found|version .* not found'; then
    echo "===== $f ====="
    echo "$result" | grep -E 'not found|version .* not found'
  fi
done
```

`GLIBC_x.y not found` 表示构建基线比目标 libc 新；`GLIBCXX_*` / `CXXABI_* not found` 表示 C++ Runtime ABI 不匹配。这属于 Native 部署问题，不是 .NET/Avalonia Managed Assembly 解析问题。

## OCCT Resources

Portable SDK 将 OCCT Resources 放在 `occt/resources`。`OcctRuntime.Configure()` 会根据实际存在的目录配置 STEP/IGES 默认资源、消息目录、Shader、Texture、Units 等路径。仅复制 Native Library 而漏掉资源，可能表现为程序能启动但导入导出或显示功能后续失败。

## 排障顺序

Native Runtime 加载失败时按以下顺序检查：

1. 进程是否 x64；
2. `runtime/OcctNative.dll` 或 `runtime/libOcctNative.so` 是否存在；
3. Native Dependency Closure 是否完整；
4. Binary/Portable Manifest 的 Source Commit 与 Hash 是否匹配；
5. `occt/resources` 是否完整；
6. Linux 系统 ABI 是否满足包内二进制要求；
7. 应用是否在创建第一个 Native-backed 对象前调用 `OcctRuntime.Configure()`。

诊断 API 会输出已配置的 Native/OCCT Root、候选 Bridge 路径、资源变量和已加载模块。Portable 布局的主 Native 文件本来就位于 `runtime/`，不要把“应用根目录缺少 flat Native 文件”误认为 Portable Runtime 本身缺失。

第三方项目的完整目录、MSBuild 引用和发布方式见 [第三方项目消费 SDK](09_第三方项目消费SDK.md)。
