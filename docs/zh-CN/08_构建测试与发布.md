# 构建、测试与发布

Bridge 3 使用同一套 ABI5-only 源码维护 Windows x64 与 Linux x64。本章明确区分 **Consumer 产物生成** 和 **Bridge 完整质量验证/正式发布**，避免下游项目每次刷新 SDK 都重复执行昂贵的 QA Gate。

`bridge-contract.json` 是 Bridge 版本、ABI、OCCT、.NET、C# 与 Consumer Framework 的机器可读事实源。

## 1. 工具链契约

Windows x64：

- Visual Studio 2022 / MSVC x64 C++ Toolchain
- 满足契约最低版本的 CMake
- OCCT 7.9.0 x64
- 从 `10.0.100` 基线按 `latestFeature` Roll-forward 解析的稳定版 .NET 10 SDK
- PowerShell

Linux x64：

- C++17 编译器与 CMake
- OCCT 7.9.0
- 与同一基线兼容的稳定版 .NET 10 SDK
- Portable SDK 打包所需 ELF 工具：`ldd`、`realpath`、`patchelf`、`sha256sum`、`python3`

Managed Binary SDK 以 .NET 8（`net8.0` / `net8.0-windows`）为最低运行时基线，同一套 Managed DLL 面向 .NET 8、9、10 Consumer。`10.0.302` 等后续稳定版 .NET 10 SDK 可以使用，不要求精确 `10.0.303`。

## 2. 两级产物模型

### 2.1 Consumer Artifact 快路径 — `dist`

当调用者只需要从一个明确 Source Revision 生成当前 Binary SDK，而**不需要重新认证 Bridge 本身**时使用 `dist`。

Windows：

```powershell
.\build.ps1 dist Release -OcctRoot "D:\tools\occt-vc144-64"
```

Linux：

```bash
./build.sh dist Release
```

快路径会执行构建脚本所需的源码/Contract Check，编译 Native + Managed，生成平台专用 Contract/Manifest，记录精确 Source Commit 并计算 Payload Hash。

它明确跳过：

- .NET 8/9/10 Consumer Matrix；
- Managed Regression Tests；
- Core Native Smoke；
- WinForms/WPF/Avalonia Viewport Smoke；
- Linux Avalonia 图形 Smoke。

这是 Demo 刷新 SDK、受控内部 Consumer 或第三方源码构建应使用的路径。

### 2.2 Bridge 完整 Gate — `sdk`、`all`、`publish`

只有在验证 Bridge 候选提交或生成正式分发制品时运行完整 Gate。

Windows 已验证 Binary SDK：

```powershell
.\build.ps1 sdk Release -OcctRoot "D:\tools\occt-vc144-64"
```

Windows 正式发布：

```powershell
.\publish.ps1 -OcctRoot "D:\tools\occt-vc144-64" -Zip
```

Linux Headless 验证/发布：

```bash
./build.sh all Release
./publish.sh
```

Windows 完整 Gate 包含 Native + Managed、Consumer Matrix、ManagedTests、Core Native Smoke 和三套 Viewport Host Smoke。正式 publish 随后生成/校验 Binary SDK 与 Portable SDK。Linux 正式 publish 保留 Headless Test/Smoke Gate；`avalonia-smoke` 是单独的 DISPLAY 相关测试。

**原则：**下游 Consumer 刷新 SDK 时不得默认调用完整 Bridge Gate，除非该流程明确承担 Bridge Release Validator 职责。

## 3. Windows build.ps1 Target

```powershell
.\build.ps1 [Target] [Configuration] [-OcctRoot <path>]
```

| Target | 职责 |
| --- | --- |
| `validate` | 静态 Repository/Contract Check |
| `native` | 构建 `OcctNative.dll` |
| `managed` | 构建 Core、WinForms、WPF、Avalonia Managed DLL |
| `consumer` | 编译支持的 .NET 8/9/10 Consumer Matrix |
| `test` | Managed Regression Tests |
| `smoke` | Core Native-backed Smoke |
| `viewport-smoke` | WinForms/WPF/Avalonia Native Host Smoke |
| `dist` | **快速 Consumer Binary SDK**：Native + Managed + Package，不跑 Regression/Smoke |
| `sdk` | **完整验证后的 Release Binary SDK**：完整 Windows Gate 后复用已验证输出打包 |
| `clean` | 删除生成输出 |
| `all` | 完整本地验证，不写入 Binary SDK |

`dist` 与 `sdk` 仅支持 Release。

## 4. Linux build.sh Target

```bash
./build.sh [target] [configuration]
```

支持：

```text
validate
native
managed
test
smoke
avalonia-smoke
dist
clean
all
```

Linux `dist` 构建 Core + Avalonia Managed DLL 和 `libOcctNative.so`，然后生成最小 linux-x64 SDK，不运行测试或 Smoke。`all` 运行 Managed Regression 与 Headless Core Native Smoke。`avalonia-smoke` 需要 X11/XWayland `DISPLAY`，普通 Consumer 同步不应触发它。

## 5. 静态 Contract Check

Windows Target 会检查版本/TFM 策略、架构边界、ABI5-only、Bulk ABI、Native Build Inventory、API Declaration/Binding 对等，以及 Consumer Framework Matrix。

这些检查相对真实 Native/UI Smoke 成本较低，适合保留在确定性 Consumer Artifact 生成过程中；但它们不等价于完整 Release Gate。

## 6. Consumer 兼容矩阵

Bridge Managed DLL 只维护一套 .NET 8 基线，仓库验证这套 DLL 能被以下项目引用：

```text
Core/Avalonia: net8.0; net9.0; net10.0
WinForms/WPF:  net8.0-windows; net9.0-windows; net10.0-windows
```

Consumer Matrix 属于 Bridge QA。Demo 或第三方项目每次刷新一个已经确定的 Bridge Source Commit 时，不需要重新编译整套矩阵。

## 7. 最小 Binary SDK 布局

Windows `dist/win-x64`：

```text
OcctNative.dll
OcctNet.dll
OcctNet.WinForms.dll
OcctNet.Wpf.dll
OcctNet.Avalonia.dll
bridge-contract.json
bridge-manifest.json
```

Linux `dist/linux-x64`：

```text
libOcctNative.so
OcctNet.dll
OcctNet.Avalonia.dll
bridge-contract.json
bridge-manifest.json
```

Manifest 记录：

- Schema Version；
- Author 与 Bridge Version；
- ABI `current` / `minimumSupported`；
- OCCT Version；
- Platform 与 Managed TFM；
- SDK Baseline 与实际 Resolved SDK；
- 精确 `sourceCommit`；
- 每个 Payload 文件的 SHA-256。

最小 SDK 故意保持小型，不包含 OCCT Native Runtime Closure。

## 8. 生成目录策略

整个 `dist/` 都是生成状态并由 Git 忽略，可随时删除后重建。`.cache/`、`build/`、`artifacts/` 同样属于本地生成状态。

不要把生成的 SDK DLL/SO Payload 提交到 `main`、`main-dev`、`demo`、`demo-dev`。第三方正式分发应进入经过审查的 Release Asset 或其它受控制品仓库。

## 9. Demo Consumer 同步

Demo 是真实 Binary SDK Consumer，不应成为第二套 Bridge Release Pipeline。

缓存命中时，Demo sync 会校验本地 Binary SDK 和 Portable SDK 是否与所选 Source Commit/Hash 匹配，然后直接返回，不编译 Bridge。

缓存失效时，新流程为：

```text
解析 origin/main 或 origin/main-dev sourceCommit
        ↓
Bridge dist Release
  仅 Native + Managed + Binary SDK
        ↓
Bridge 自己的 Portable SDK Packager
        ↓
校验 Contract / sourceCommit / Hash
        ↓
复制到 Demo dist Cache
```

同步阶段**不会**调用 Bridge `sdk`、`all`、ManagedTests、Core Smoke 或任何 Viewport/窗口 Smoke。

如果正式 Bridge Publish 已经生成完全匹配的 Binary SDK 与 Portable SDK，Demo 可以通过 Windows `-SdkRoot` / `-PortableRoot`，或 Linux `--sdk-root` / `--portable-root` 直接消费，Bridge 编译次数为 0。

## 10. 正式发布

`publish.ps1` / `publish.sh` 是 `main-dev` 候选验证和 `main` 正式制品的受控入口，要求干净源码树，并对当前分支和对应远端分支做 Ancestry 校验。

推荐提升流程：

```text
main-dev candidate
  ↓ full publish gate
验证精确 commit
  ↓ 仅 fast-forward
main
  ↓ formal publish
经审查 Release Artifacts
```

已经验证的候选在提升过程中不要再引入另一组源码修改。

## 11. 第三方 Consumer 策略

第三方项目通常应消费从正式 `main` 生成并经过审查的 SDK，而不是 `main-dev`。

产物职责：

- Binary SDK：编译引用、CI Metadata/Hash 校验；
- Portable SDK：部署阶段 Native/OCCT Closure 与 Resources。

第三方项目接受 SDK 前应验证 Platform、ABI、Bridge Version/Source Identity 和 Hash；升级时 Managed + Native + Runtime/Resources 必须作为一个整体替换。完整示例见 [第三方项目消费 SDK](09_第三方项目消费SDK.md)。

## 12. Linux 分发兼容性

Linux Portable SDK 并不会消除 glibc/libstdc++ ABI 要求。Native Bridge 与 OCCT 必须在**不高于最老目标系统**的 ABI 基线上编译。AppImage 也不能修复一个已经链接到更新 `GLIBC_*`、`GLIBCXX_*`、`CXXABI_*` 的二进制。

详见 [运行时部署与诊断](07_运行时部署与诊断.md)。

## 13. 文档与 API Surface 策略

仓库维护手工编写的架构、接入、构建、部署和迁移文档，不生成逐类型/逐方法 API Reference。Native/Managed API 对等继续由源码级验证负责。
