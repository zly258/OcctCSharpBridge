# 构建、测试与发布

Bridge 3 在同一 ABI5-only 源码树中维护 Windows 与 Linux x64 构建链。源码契约要求**精确使用 .NET SDK 10.0.302**，`global.json` 禁止 SDK roll-forward。Windows 使用 PowerShell，Linux 使用 `build.sh`。

Windows x64：

```powershell
.\build.ps1 validate Release
.\build.ps1 native Release -OcctRoot "D:\tools\occt-vc144-64"
.\build.ps1 managed Release
.\build.ps1 test Release
.\build.ps1 smoke Release -OcctRoot "D:\tools\occt-vc144-64"
.\build.ps1 docs Release
.\build.ps1 dist Release -OcctRoot "D:\tools\occt-vc144-64"
```

Linux x64：

```bash
./build.sh validate Release
./build.sh managed Release
./build.sh native Release
./build.sh test Release
./build.sh smoke Release
./build.sh dist Release
```

完整且不生成仓库产物的验证，两端统一使用 `all`：

```powershell
.\build.ps1 all Release
```

```bash
./build.sh all Release
```

`all` 会执行静态 Contract Checks、Native Build、Managed Build、Managed Regression Tests 和 Native Smoke。`docs` 与 `dist` 会生成仓库产物，因此保持显式独立 target，不包含在 `all` 中。

静态校验覆盖精确的 Bridge/.NET/OCCT/ABI 契约、架构边界、Bulk Snapshot/Buffer 策略、Native Source Inventory，以及 Native/Managed API Surface 的精确对等。Bridge 3 不保留 ABI 4 兼容文件、Handle、导出、Manifest 或旧 Consumer 测试。

Windows `managed` 构建：

```text
OcctNet
OcctNet.WinForms
OcctNet.Wpf
OcctNet.Avalonia
```

Linux 托管构建只包含跨平台的 `OcctNet` 与 `OcctNet.Avalonia`；WinForms、WPF 保持 Windows-only。

Windows `dist` 输出 `dist/win-x64`，包含 `OcctNative.dll`、核心托管程序集以及三个 Windows 可消费 UI Adapter，其中包括 `OcctNet.Avalonia.dll`。Linux `dist` 输出 `dist/linux-x64`，包含 `libOcctNative.so`、`OcctNet.dll` 与 `OcctNet.Avalonia.dll`。

两个 Binary SDK 都携带 Bridge 3 schema-3 `bridge-contract.json` 和 schema-2 `bridge-manifest.json`。Manifest 使用嵌套 ABI5 元数据：

```json
"nativeAbi": {
  "current": 5,
  "minimumSupported": 5
}
```

旧的 flat `nativeAbiVersion` 字段禁止重新引入。

## 正式 Windows 发布验证

在干净且已与远端同步的正式 `main` 分支执行：

```powershell
.\publish.ps1 -OcctRoot "D:\tools\occt-vc144-64"
```

`publish.ps1` 现在明确是**只验证、不修改 Git 历史**的发布验证脚本。它会检查生成 API 文档是否最新、构建 Release Binary SDK、验证 ABI5 Contract/Manifest、精确 Source Commit 和 SHA-256 Hash，并确保除 `dist/win-x64` 外没有意外工作区变更。

它不会执行 `git add`、不会创建 Commit，也不会直接 Push `main`。生成结果应通过正常受审查的 Git 流程发布。当前流程不使用 GitHub Actions，也不使用 NuGet 发布流水线。
