# 07 运行时部署与诊断

`OcctCSharpBridge` 明确区分 **Managed SDK** 与 **Native OCCT Runtime**。Managed NuGet 提供 .NET API；真正运行 OCCT 还需要匹配的 `OcctNative.dll`、OCCT `TK*.dll`、VC++ Runtime 和其它 Native 依赖。

## 1. Managed 包

```powershell
.\build.ps1 pack Release
```

生成：

```text
OcctNet
OcctNet.WinForms
OcctNet.Wpf
OcctNet.Avalonia
```

Managed 包包含：

- Managed Assembly；
- IntelliSense XML；
- PDB/Symbol Package；
- README；
- LICENSE；
- Managed NuGet 依赖。

当前明确不包含：

- `OcctNative.dll`；
- OCCT `TK*.dll`；
- OCCT 第三方 Native DLL；
- OCCT Resource 目录。

## 2. 推荐部署方式

正式桌面应用优先使用 **app-local Native Runtime**：

```text
MyApplication.exe
OcctNet.dll
OcctNet.Wpf.dll
OcctNative.dll
TKernel.dll
TKMath.dll
TKBRep.dll
...
```

具体 OCCT DLL 闭包取决于 Bridge 实际链接的 Toolkit 和第三方依赖。

app-local 的优点：

- 不依赖全局 PATH；
- 不容易误加载另一套 OCCT；
- 应用升级时版本边界清晰；
- 诊断简单。

## 3. 开发环境显式配置

如果 Native Bridge 和 OCCT SDK 不在应用目录，可以在第一次创建 `OcctEngine` / `OcctModelingSession` 前配置：

```csharp
OcctRuntime.Configure(
    occtRoot: @"D:\tools\occt-vc144-64",
    nativeBridgeDirectory: @"D:\workspace\OcctCSharpBridge\build\native\bin\Release");
```

也支持环境变量：

```text
OCCT_BRIDGE_NATIVE_DIR
OCCT_ROOT
CASROOT
```

同一进程启动后不要在不同位置反复切换 Runtime。

## 4. 结构化诊断

```csharp
var info = OcctRuntime.GetDiagnosticInfo();
```

诊断快照用于查看：

- Process Architecture；
- Application Base Directory；
- app-local `OcctNative.dll` 是否存在；
- app-local `TKernel.dll` 是否存在；
- 已配置 Native Directory；
- 已配置 OCCT Root/CASROOT；
- 预期 Bridge/Kernel 路径是否存在；
- 当前进程实际 Loaded Bridge 路径；
- 当前进程实际 Loaded OCCT Kernel 路径。

`GetDiagnosticInfo()` 是观察操作，不应该为了“诊断”而修改 DLL 搜索路径或强制加载 Native 模块。

## 5. 文本诊断报告

需要直接写日志或复制给开发人员时：

```csharp
Console.WriteLine(OcctRuntime.GetDiagnosticReport());
```

它适合记录：

- Runtime 配置状态；
- BaseDirectory；
- app-local 文件状态；
- 配置路径；
- Repository Probing；
- Native Bridge 候选路径；
- OCCT Resource 环境变量；
- 已加载模块。

诊断报告可能包含本机用户名、工程目录或网络路径，对外发送前应检查是否需要脱敏。

## 6. Win32 Error 126

`126` 通常表示系统无法加载某个 DLL 或其依赖，并不一定是 `OcctNative.dll` 文件本身不存在。

推荐按顺序检查：

1. 当前进程是否 x64；
2. `OcctNative.dll` 是否存在于 app-local 或配置目录；
3. `TKernel.dll` 是否存在；
4. 其它 OCCT Toolkit DLL 是否完整；
5. VC++ Runtime 是否可用；
6. FreeType/TBB 等第三方依赖是否可解析；
7. 是否意外从 PATH 加载旧版 OCCT；
8. Bridge、OCCT Header/Lib/Runtime 是否来自同一套 7.9.0 构建。

结构化判断示例：

```csharp
var info = OcctRuntime.GetDiagnosticInfo();

if (!info.ApplicationNativeBridgeExists)
{
    // app-local 没有 OcctNative.dll
}

if (info.ConfiguredNativeBridgeExists == false)
{
    // 配置目录存在问题
}

if (info.ConfiguredOcctKernelExists == false)
{
    // OCCT_ROOT/CASROOT 与预期目录结构不匹配
}
```

## 7. 版本匹配

运行时必须保证以下组件来自兼容构建：

```text
OcctNet
对应 UI Host
OcctNative.dll
OCCT Runtime
```

`OcctBridgeInfo.EnsureCompatible()` 会在 Managed/Native 入口检查 Bridge ABI 等基础契约，但它不能替代完整 Native DLL 依赖闭包验证。

## 8. .NET Runtime

当前 Target Framework：

```text
net10.0-windows
```

Framework-dependent 桌面应用需要 .NET 10 Desktop Runtime。仓库固定 SDK `10.0.302` 用于可重复构建，但运行时不应把应用锁死到某一个 `10.0.x` Patch。

## 9. Avalonia

`OcctNet.Avalonia` 当前仍是 Windows HWND Host，因此：

- NuGet 可以被 Avalonia Windows 项目引用；
- 不代表 `OcctNative.dll` 可以直接在 Linux/macOS 使用；
- 真正跨平台需要为 OCCT Viewer 的原生窗口和图形上下文单独实现后端。

## 10. 正式发布前

在目标 Windows x64 + OCCT 7.9.0 环境至少执行：

```powershell
.\build.ps1 smoke Release
```

如果 SDK 不在默认路径：

```powershell
.\build.ps1 smoke Release -OcctRoot "E:\SDK\occt-7.9.0"
```

只有真实 Native Smoke 成功，才能证明当前 Bridge 与本机 OCCT 的编译、链接、加载和核心几何执行链路正常。
