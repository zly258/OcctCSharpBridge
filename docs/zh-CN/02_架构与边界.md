# 02 架构与边界

`OcctCSharpBridge/main` 的目标是提供一个**可被多个 CAD/BIM 应用复用的 OCCT Bridge**，而不是实现完整 CAD 产品框架。

## 1. 总体分层

```text
CAD / BIM Application
├─ Document / Feature / Entity
├─ Command / Tool / Snap / Grip
├─ Undo / Redo / Persistence
└─ Product UI / Business Rules
              │
              ▼
Reusable .NET Bridge
├─ OcctEngine
├─ OcctModelingSession
├─ Runtime / Diagnostics / Value Types
└─ WinForms / WPF / Avalonia Viewport Host
              │
              ▼
Stable C ABI
              │
              ▼
Open CASCADE Technology 7.9.0
```

## 2. Native 与 Managed 边界

`src/OcctNative` 使用 C++17 调用 OCCT，并通过 `extern "C"` 暴露稳定 C ABI。跨 ABI 只传固定宽度整数、`double`、Plain Struct、UTF-8 字符串和显式 Buffer/Capacity，不暴露 STL、OCCT Handle、C++ 模板或异常。

`src/OcctNet` 把 Native ABI 提升为强类型 .NET API：

- `OcctEngine`：Viewer/AIS、显示对象、选择、Camera、外观、Annotation 与交互；
- `OcctModelingSession`：Headless 建模、拓扑、Boolean/Feature/Healing、Mesh、History、Inspection、Topology Reference 与数据交换；
- `OcctRuntime`：Native DLL 与 OCCT Runtime 探测、配置和诊断。

## 3. Owner-aware 对象

Bridge 中的对象 ID 只在所属 Engine/Session 内有意义。不同 Owner 中数值相同的 ID 不是同一对象，因此 Managed Handle 同时携带 Owner 身份，公开 API 在进入 Native 前验证所有权。

## 4. 生命周期与线程模型

`OcctEngine` 与 `OcctModelingSession` 由 SafeHandle 管理 Native 根对象生命周期，并保证 `Dispose()` 幂等。当前支持模型为：

- 同一 Engine/Session 的 Native 操作由调用方串行化；
- `Dispose()` 不与同一实例正在执行的 Native 调用并发；
- Viewer/Host 生命周期绑定创建它的 Windows HWND/UI Thread；
- 后台并行建模使用彼此独立的 `OcctModelingSession`。

这里不声明任意 Native 调用天然线程安全。

## 5. UI Host 边界

`OcctNet.WinForms`、`OcctNet.Wpf`、`OcctNet.Avalonia` 只负责 UI Framework 与 `OcctEngine` 的适配，例如 HWND、Resize、Mouse Capture、Pan/Rotate/Zoom、Hover、Rectangle Selection、DPI 与窗口生命周期。

Host 不包含 CAD Document、Command、Feature Tree、业务 Property Panel、项目文件或专业规则。

## 6. `main` 明确不包含

- Document / DocumentManager；
- Entity / Feature Tree；
- Command / Tool / Registry；
- Snap / Grip；
- Undo / Redo；
- JSON 项目持久化；
- Ribbon、PropertyGrid、Workspace 等产品 UI；
- BIM/设备专业业务规则；
- OCAF/XDE。

## 7. 分支职责

### `main`：唯一 Bridge 源码生产者

```text
src/OcctNative
src/OcctNet
src/OcctNet.WinForms
src/OcctNet.Wpf
src/OcctNet.Avalonia
tests
tools/OcctApiDocsGenerator
docs/zh-CN
docs/en-US
build.ps1
publish.ps1
dist/win-x64
```

`dist/win-x64` 是通过真实 Release Build、Managed Test、Native Smoke 后形成的正式 Binary SDK。

### `demo`：Binary SDK 消费验证

Demo 只维护应用层源码：

```text
src/OcctDemo.Common
src/OcctDemo.WinForms
src/OcctDemo.Wpf
src/OcctDemo.Avalonia
dist/win-x64
```

Demo 不包含 `src/OcctNative`、`src/OcctNet*` 或 Bridge 自身 tests。这样 Demo 本身就是“外部项目只拿 DLL 能否正常使用 Bridge”的真实验证。

### 其它应用

OCStation 等外部项目应消费 `dist/win-x64` 发布出来的 Binary SDK，而不是 clone、checkout、编译整个 Bridge 仓库。

## 8. `main → demo` 发布规则

仓库不使用 GitHub Actions 自动覆盖分支。正式发布入口统一为：

```powershell
.\publish.ps1 -OcctRoot "D:\tools\occt-vc144-64"
```

流程：

```text
main source change
    ↓
build.ps1 dist Release
    ↓
all + managed test + native smoke
    ↓
生成/校验 dist/win-x64
    ↓
commit + push main
    ↓
临时 detached git worktree 打开 demo
    ↓
只同步 dist/win-x64
    ↓
校验 Contract / Manifest / SHA-256
    ↓
commit + push demo
```

同步单位只有 Binary SDK，不再跨分支复制 Bridge 源码。`publish.ps1` 不切换当前开发目录的分支。

## 9. 无旧兼容层原则

不重新引入：

- `Legacy*` 类型/方法；
- 仅转发到新 API 的旧 Alias；
- 已删除头文件的兼容壳；
- 为旧 Demo API 修改核心 Bridge 设计。

上层调用不匹配时修改调用方，而不是恢复历史接口。

## 10. 新能力进入 `main` 的判断标准

1. 是否直接封装 OCCT 能力，或属于通用 Bridge/Runtime/Viewport Host？
2. 是否能被多个不同上层应用复用，而不依赖业务 Document？
3. 是否能形成稳定、强类型、可测试的 C ABI + Managed API？

主要依赖产品数据模型、命令状态或业务流程的能力留在应用层。
