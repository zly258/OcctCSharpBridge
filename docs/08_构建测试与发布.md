# 08 构建测试与发布

`build.ps1` 是本仓库本地验证、构建、打包和 Native Smoke 的统一入口。构建配置应从代码和 `bridge-contract.json` 获取，不让 README/docs 文案成为构建成功的必要条件。

## 1. `bridge-contract.json`

当前机器可读契约包括：

- Bridge Version；
- Native ABI Version；
- OCCT Version；
- Platform；
- CMake Minimum Version；
- .NET Target Framework；
- .NET SDK Version；
- C# Language Version；
- Native/Managed/Public API 数量。

当这些值变化时，应该先修改 Contract，再同步真正依赖这些值的构建和代码位置。

文档可以展示 Contract 的当前值，但文档不是第二份配置文件。

## 2. build target

### `validate`

执行静态仓库契约检查，不编译 Native OCCT。

```powershell
.\build.ps1 validate Release
```

### `managed`

构建 Core、WinForms、WPF、Avalonia，并运行不依赖 OCCT 的 Managed 回归。

```powershell
.\build.ps1 managed Release
```

### `native`

使用 CMake + MSVC + 指定 OCCT SDK 构建 `OcctNative.dll`。

```powershell
.\build.ps1 native Release
```

### `pack`

生成 Managed NuGet/Symbol Package，并校验包内容边界。

```powershell
.\build.ps1 pack Release
```

### `smoke`

构建并加载真实 Native Bridge，执行 OCCT 几何/拓扑场景。

```powershell
.\build.ps1 smoke Release
```

### `ci`

用于不依赖本机 OCCT SDK 的云端检查组合。

### `all`

从静态校验开始执行完整本地流程。

```powershell
.\build.ps1 all Release
```

## 3. 测试分层

### A. 静态契约

`tests/check-*.ps1` 适合检查**仓库结构层面、不运行程序也能确定的事实**，例如：

- Native Declaration 与 Definition 是否对应；
- P/Invoke 是否有对应 Native Export；
- CallingConvention/ExactSpelling 是否满足规则；
- Modeling 集合是否回退成 `Count + At`；
- OCAF/XDE 是否重新进入 Bridge；
- UI Host 是否破坏层次边界；
- NuGet 是否错误捆绑 Native Runtime；
- Contract 版本与真正构建配置是否一致。

### B. Managed 回归

验证不需要加载 OCCT 的行为：

- 值类型；
- Guard；
- Owner-aware 语义；
- Runtime Diagnostics 的无副作用行为；
- Geometry Extensions；
- DTO/Result Mapping；
- Viewport Interaction Policy。

### C. Native Smoke

必须使用真实 OCCT 7.9.0，覆盖：

- Native DLL 加载；
- 基础几何创建；
- Boolean/Feature；
- Topology；
- Mesh；
- 数据交换；
- P0–P3 关键能力。

## 4. PowerShell 契约检查应该检查什么

PowerShell Contract Check 本身不是问题，问题是**检查目标是否属于静态契约**。

适合：

```text
Native 导出了某函数，但 Managed 没有对应 P/Invoke
某个禁止的 OCAF 文件重新出现
Bulk API 被改回逐项读取
项目 TargetFramework 偏离 bridge-contract.json
```

不适合：

```text
README 必须包含某一段固定英文
文档文件名必须是某个旧名字
build.ps1 必须逐字包含某个固定字符串
为了验证代码功能而大量解析源代码文本
```

后一类检查容易造成“实现完全正确，只是换行/重构/改文档名字就失败”。

## 5. 当前优化原则

后续 Contract Check 应遵循：

1. **优先验证事实，不验证写法。**
2. **能用编译/测试验证的，不用字符串搜索代替。**
3. **文档不参与功能构建门禁。**
4. **代码组织检查只保留真正的架构红线。**
5. **同一规则只保留一个检查位置。**
6. **错误信息必须说明实际不变量，而不是要求开发者复制某段固定文本。**

## 6. 版本来源

Managed Package Version 应从：

```text
bridge-contract.json -> $BridgeVersion -> dotnet build/pack property
```

传递。

检查器应该验证“版本确实来自 Contract 并传给构建”，而不是要求 `build.ps1` 必须以某一种精确排版书写。

## 7. 为什么本地会出现 Version Contract 报错

如果看到：

```text
Managed builds must use bridge-contract.json as the package version source.
```

说明当前 `check-version-contract.ps1` 没有识别到 `build.ps1` 中的版本传递写法。

排查顺序：

```powershell
git status
git diff -- build.ps1 tests/check-version-contract.ps1
git rev-parse HEAD
git log -1 --oneline
```

然后确认 `build.ps1`：

- 读取了 `bridge-contract.json`；
- 将 `contract.bridgeVersion` 赋给 `$BridgeVersion`；
- 在 Managed build/pack 时把 `$BridgeVersion` 传给 MSBuild/NuGet。

如果这些事实成立但仍失败，说明检查器过度依赖固定字符串，应优化检查器，而不是为了迎合检查器把正确代码改回固定排版。

## 8. API 数量

Native/Managed API 数量适合作为 Release Contract 的快速异常检测，但不能替代签名级 ABI 校验。

例如以下变化仅靠“348 == 348”无法发现：

- `double` 改成 `float`；
- 参数顺序变化；
- Struct 字段顺序变化；
- Enum 数值变化；
- `int64` 误改成 `int32`。

后续 ABI 检查应逐步增加：

- Return Type；
- Parameter Type/Order；
- Struct `sizeof`；
- Struct `offsetof`；
- Enum Numeric Value。

## 9. Release 前建议门禁

至少完成：

```powershell
.\build.ps1 validate Release
.\build.ps1 managed Release
.\build.ps1 pack Release
.\build.ps1 smoke Release
```

并检查：

- `bridge-contract.json` 已更新；
- README 与主要文档没有明显过时版本号；
- Native/PInvoke 对等；
- Managed Package 不包含错误的 Native DLL；
- Demo 分支需要复用的 Bridge 源码已同步；
- 真实 OCCT 7.9.0 Smoke 通过。

## 10. 不把开发流水账放进 docs

阶段计划、临时 TODO、一次性修复记录不作为长期文档保留。需要追踪历史时使用 Git Commit、Issue 或 PR。

`docs` 只保存未来仍需要阅读的架构、使用、部署和验证说明。
