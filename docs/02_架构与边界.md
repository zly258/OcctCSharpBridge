# 02 架构与边界

`OcctCSharpBridge` 的目标是提供一个**可被多个 CAD/BIM 应用复用的 OCCT Bridge**，而不是在 `main` 中实现完整 CAD 产品框架。判断一个能力是否应该进入 `main`，首先看它是否属于 OCCT 本身或 OCCT 与 .NET/UI Host 之间的稳定桥接职责。

## 1. 总体分层

```text
CAD / BIM Application
├─ Document / Feature / Entity
├─ Command / Tool / Snap / Grip
├─ Undo / Redo / Persistence
└─ Product UI / Business Rules
              │
              ▼
Reusable .NET Bridge
├─ OcctEngine
├─ OcctModelingSession
├─ Runtime / Diagnostics / Value Types
└─ WinForms / WPF / Avalonia Viewport Host
              │
              ▼
Stable C ABI
              │
              ▼
Open CASCADE Technology 7.9.0
```

## 2. `src/OcctNative`

Native 层使用 C++17 调用 OCCT，并通过 `extern "C"` 暴露稳定 C ABI。这样可以避免把 OCCT C++ 类型、模板、Handle 或异常直接暴露给 .NET。

主要职责：

- Viewer/AIS 生命周期与显示对象；
- Primitive、Curve、Surface、B-Rep 建模；
- Boolean、Feature、Healing；
- Topology、History、分析与投影；
- Mesh 与数据交换；
- 将 OCCT 结果转换成 ABI 可稳定传输的结构体、枚举、ID 和批量数组。

C ABI 应保持简单：固定宽度整数、`double`、Plain Struct、UTF-8 字符串、显式 Buffer/Capacity。不要跨 ABI 暴露 STL 容器或 OCCT C++ 对象。

## 3. `src/OcctNet`

Managed Core 不重新实现 OCCT，而是把 Native ABI 提升成强类型 .NET API。

两个主要 Facade：

- `OcctEngine`：有 Viewer/AIS Context 的交互式场景；
- `OcctModelingSession`：无 HWND 的 Headless 建模场景。

其它核心职责包括：

- `OcctRuntime`：Native DLL 与 OCCT Runtime 配置、探测和诊断；
- Owner-aware Handle：阻止不同 Engine/Session 的对象被错误混用；
- `OcctGeometryExtensions`：不依赖 Native 的轻量级值类型计算；
- DTO/Result 类型：把 Native 结果转换成清晰、不可误用的 Managed 语义。

## 4. Owner-aware 对象

Bridge 中的对象 ID 只在所属 Engine/Session 内有意义。

```text
OcctEngine A -> Object 12
OcctEngine B -> Object 12
```

两个 `12` 并不是同一个对象。因此 Managed Handle 同时携带 Owner 身份，公开 API 在进入 Native 前检查所有权。

同样：

```text
OcctModelingSession A -> Shape 8
OcctModelingSession B -> Shape 8
```

不能因为 ID 相同就跨 Session 使用。

这种设计比让上层长期保存裸 `long` 更安全，也是 `main` 公共 API 的基本约束。

## 5. Native 生命周期

`OcctEngine` 与 `OcctModelingSession` 都通过 `SafeHandle` 管理 Native 根对象释放，同时使用 Managed Dispose 状态阻止对象释放后继续调用。

Native 资源管理的原则是：

- 创建和销毁必须成对；
- Native 异常不能穿过 C ABI；
- Managed Dispose 必须幂等；
- 子对象使用稳定 ID/Owner 语义，不直接把任意 Native 指针交给业务层保存。

## 6. `OcctEngine` 与 `OcctModelingSession` 为什么不合并

两者会有少量几何创建能力重叠，但用途不同：

### `OcctEngine`

面向交互式 Viewer：

- 创建/注册可显示对象；
- AIS Selection；
- Camera/View；
- 外观、Transform、Annotation；
- 鼠标交互和视口状态。

### `OcctModelingSession`

面向几何内核和批处理：

- Headless 建模；
- 大量拓扑查询；
- Boolean/Feature/Healing；
- Mesh；
- STEP/IGES/BREP/STL；
- History、Inspection、Topology Reference。

为了消除少量表面重复把两者合成巨型类，会把窗口生命周期与 Headless 建模强耦合，因此不采用这种设计。

## 7. UI Host 边界

```text
OcctNet.WinForms
OcctNet.Wpf
OcctNet.Avalonia
```

只负责 UI 框架与 `OcctEngine` 之间的适配，例如：

- 创建/销毁 HWND；
- Resize；
- Mouse Capture；
- Pan / Rotate / Zoom；
- Hover；
- Rectangle Selection；
- DPI 和窗口生命周期适配。

Host 不应该包含：

- CAD Document；
- Command 系统；
- Feature Tree；
- 业务属性面板；
- 项目文件；
- 专业规则。

WinForms、WPF、Avalonia 的窗口模型不同，不为了形式上的 DRY 强制建立一个脆弱的跨框架 UI 基类。可共享的是无 UI 依赖的交互策略，而不是具体控件生命周期。

## 8. `main` 不包含的内容

以下能力明确属于上层应用：

- Document / DocumentManager；
- Entity / Feature Tree；
- Command / Command Registry；
- Tool / Tool Manager；
- Snap / Grip；
- Undo / Redo；
- JSON 项目持久化；
- Ribbon、PropertyGrid、Workspace 等产品 UI；
- BIM/设备专业数据和业务规则。

`main` 同样不引入 OCAF/XDE。应用如果需要自己的文档、事务和持久化模型，应在 Bridge 之上实现，而不是重新把应用框架塞回 Native 封装。

## 9. 分支职责

### `main`

可复用 Bridge、UI Host、测试、文档与 SDK 打包。

### `demo`

基于同一 Bridge 展示完整应用层做法和可运行示例。Demo 可以有 Document、Command、Tool 等，但这些不是 `OcctNet` API。

### `website`

项目网站，只展示公开项目能力，不参与 Bridge 运行时实现。

## 10. 设计判断标准

新增能力进入 `main` 前至少回答三个问题：

1. 是否直接封装 OCCT 能力，或属于通用 Bridge/Runtime/Viewport Host？
2. 是否可以被多个不同上层应用复用，而不依赖具体业务 Document？
3. 是否能形成稳定、强类型、可测试的 C ABI + Managed API？

如果答案主要依赖某个产品的数据模型、命令状态或业务流程，则应该留在应用层。
